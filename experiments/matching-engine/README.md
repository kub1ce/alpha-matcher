## Исторический базовый сценарий

Ниже сохранено описание первого этапа, включая его первоначальные ограничения. Оно объясняет исходную модель данных и контрольные примеры. Ограничения на длину текста и отсутствие обработки ФИО в этом описании относятся к первой реализации. Для текущего accepted engine действует [контракт передачи Stage 7](stage6/final-acceptance/STAGE7_ENGINE_HANDOFF.md).

Для воспроизведения ранних проверок сохранены [протокол этапа 3](stage3/PROTOCOL.md), baseline и корпуса. `Run-MySqlTests.ps1 -Stage3Phase final` запускает соответствующие проверки. Исторические замеры `-Stage2` используют `stage3/baseline-pom.xml` для совместимости с V2-эталоном.

Модуль Java 25 + JDBC + MySQL отделён от основного приложения. Предпросмотр не подтверждает привязки и не меняет `operation.contract_id`, статусы или сохранённых кандидатов. Текущий UI Stage 7 подключает accepted engine отдельной зависимостью.

## Что найдено в исходном проекте

- `src/main/resources/db/migration/V1__initial_schema.sql` и `database/schema.sql` имеют
  одинаковые исполняемые определения таблиц; различаются закомментированными заготовками валют.
- У договора нет прямого `client_id`: участники находятся в `contract_party` с ролями
  `PAYER`, `RECIPIENT`, `BENEFICIARY`. У операции роли `PAYER`, `RECIPIENT`.
  Для одной сущности действует UNIQUE по `(contract_id/operation_id, role_id)`.
- `client_id` у участника необязателен; исходный ИНН может храниться непосредственно
  в `contract_party.inn` / `operation_party.inn`. Он не должен противоречить связанному клиенту.
- Номер договора индексирован, но НЕ уникален. Первый найденный договор выбирать нельзя.
- SQL-статусы операции: `LOADED`, `REJECTED`, `PROCESSED`. Отдельной ручной очереди в схеме нет.
  `operation_contract_candidate` содержит подсказки, а не подтверждённые связи.
- `contract_date` - дата договора, не окончание действия. В правилах срока действия нет.
- Основной `BasicPaymentPurposeParser` использует регулярные выражения и контрольные цифры ИНН.
  `DemoMatchingService` получает кандидатов из фикстур, а не ищет их в MySQL.
  Его тесты подтверждают разделение предпросмотра/применения и отказ от неоднозначной автопривязки.
- Корневой Maven использует Java 25, Spring Boot и Vaadin. Этот `pom.xml` не наследует его
  и не содержит UI/Spring-зависимостей. Сравнительный анализ алгоритмов по именам файлов
  в доступных исходных документах не обнаружен; конкретный внешний анализ не использован.

## Вертикальный сценарий

`Main -> MatchingEngine -> PurposeParser -> JdbcMatchingRepository -> MySQL -> Decision`

1. Операция и её участники загружаются одним SELECT.
2. Парсер нормализует пробелы/дефисы, извлекает явно помеченные ИНН и номера договоров.
   Формат и контрольные цифры ИНН проверяются; нулевые значения не принимаются.
3. Поиск использует равенство по `contract.contract_number`. Без явного номера - поиск
   по ИНН клиента и исходному ИНН стороны договора. Параметры передаются через PreparedStatement.
   Индексируемые колонки не оборачиваются в SQL-функции.
4. Проверяются оба участника с сохранением роли, ИНН, согласованность исходного ИНН и ИНН
   клиента, а также равенство `client_id`, если идентификатор есть с обеих сторон.
5. Результат содержит извлечённые значения, IDs кандидатов и список выполненных проверок
   с объяснениями. Никаких выдуманных процентов уверенности.

**SAFE** допускается только для непривязанной `LOADED`-операции: один явный номер, один
кандидат с точно совпавшим нормализованным номером, корректные согласованные данные двух
ролей, хотя бы один ИНН из назначения и отсутствие противоречий между извлечёнными ИНН
и участниками. Отличающийся/неподтверждённый выгодоприобретатель либо распознанный признак
платежа за третье лицо требует **REVIEW**. Это консервативное ограничение прототипа,
а не проверенная на банковской выборке полнота распознавания третьих лиц.

**NO_CONTRACT** означает: поддерживаемые ключи поиска есть, но поиск не дал кандидатов.
Отсутствие ключей, неверные или неполные реквизиты, несколько номеров/кандидатов дают
**REVIEW**. Уже привязанная, отклонённая или обработанная операция даёт **SKIPPED**.
**ALREADY_MANUAL** сохранён в enum для согласованности, но не выдаётся: SQL-данных очереди нет.
Статусы результата не записываются в справочник `operation_status` и не подменяют его.

Нужна транзакция `REPEATABLE_READ`, `autoCommit=false`: чтения одного предложения имеют
согласованный снимок. Это ещё не механизм конкурентного применения результатов.
Вход длиннее 4000 символов отклоняется явной ошибкой. Сопоставления ФИО и склонений пока нет.
Нормализуются ключи входного текста; SQL-поиск рассчитан на канонически записанные номера
в БД. Массовая нормализация реальных справочников здесь не реализована.

## Воспроизводимые тесты

Требуются Java 25, Maven 3.9+ (или корневой Wrapper), Docker с Linux Engine;
для `Run-MySqlTests.ps1` - PowerShell 7+.
Unit-тесты не требуют Docker. Из корня проекта:

```powershell
.\mvnw.cmd -f experiments/matching-engine/pom.xml test
.\experiments\matching-engine\Run-MySqlTests.ps1
```

Вторая команда поднимает MySQL 8.4.8 с закреплённым digest, выполняет
`-Pmysql-it verify` и удаляет только созданный ею compose-проект. Нет H2, моков SQL
или автоматического пропуска integration-тестов при недоступной БД.
При уже существующих контейнерах этого эксперимента скрипт останавливается без их удаления.

БД `matching_engine_exp` создаётся только в отдельном контейнере, данные находятся в tmpfs.
Порт `33077` доступен только через `127.0.0.1`. Пароль тестового пользователя генерируется
на время запуска; исходные значения переменных среды восстанавливаются. Контейнер не
использует существующие MySQL-сервисы или тома. Клиентский код дополнительно проверяет
имя БД, локальный JDBC URL и тип сервера MySQL.

`sql/001_schema.sql` - локальная копия реальной миграции; изменён только выбор БД и явно
задана кодировка SQL-соединения. SHA256 источника указан в заголовке. Исходная миграция
не исполняется напрямую: её `CREATE DATABASE/USE alpha_matcher` сюда не допускается.
Кодировка сервера/БД - `utf8mb4` / `utf8mb4_unicode_ci`, как в исходной схеме.

`src/test/resources/fixtures.sql` содержит 20 фиксированных вымышленных операций и 9
договоров. Эталон `cases.csv` написан по сценариям независимо от Matching Engine:
4 SAFE, 12 REVIEW, 1 NO_CONTRACT, 3 SKIPPED. Это контрольные примеры, не оценка
точности на репрезентативной банковской выборке и не полноценный генератор.

Integration-тесты проверяют весь путь от SQL-текста до решения, 10-/12-значные ИНН,
дубли номеров, внешние стороны без client_id, конфликты идентификаторов, роли, выгодоприобретателя,
старую дату договора, неизменность шести таблиц и повторяемость предпросмотра.
Пробная правка реквизита внутри тестовой транзакции откатывается.
XML-результаты Maven: `target/surefire-reports/` и `target/failsafe-reports/`.

## Самостоятельный запуск CLI

Для ручного исследования можно отдельно поднять тот же пустой одноразовый контейнер
с контрольными примерами. Из корня проекта, в одной PowerShell-сессии:

```powershell
$env:MATCHING_DB_PASSWORD = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24))
$env:MATCHING_DB_USER = 'matcher'
$env:MATCHING_DB_URL = 'jdbc:mysql://127.0.0.1:33077/matching_engine_exp?characterEncoding=UTF-8&connectionTimeZone=UTC&connectTimeout=5000&socketTimeout=15000&allowPublicKeyRetrieval=true&sslMode=DISABLED'
docker compose -f experiments/matching-engine/compose.yaml up -d --wait --wait-timeout 180
.\mvnw.cmd -f experiments/matching-engine/pom.xml -q compile exec:java "-Dexec.args=1"
docker compose -f experiments/matching-engine/compose.yaml down --volumes
```

ID 1 - SAFE, 2 - REVIEW, 3 - NO_CONTRACT. Пароль не надо выводить или сохранять в Git.
Запрет TLS в примере относится только к этому локальному одноразовому стенду.
Вне репозитория модуль собирается обычным `mvn test` / `mvn -Pmysql-it verify`.

## Следующий этап, не выполненный сейчас

- Детерминированный настраиваемый генератор и независимый большой эталон, включая ФЛ/ИП/ЮЛ,
  одинаковые/склонённые ФИО, неканонические номера и сложные назначения.
- Отдельный компонент обработки склонений без механического удаления окончаний.
- Измерение ложноположительных SAFE, полноты, извлечения признаков и долей статусов.
- Опциональная экспериментальная миграция индексов с проверкой эквивалентных индексов:
  `ix_client_fio`, `ix_contract_party_client_role`, `ix_contract_party_inn_role`,
  `ix_operation_status_date`. Сейчас используются только индексы исходной схемы.
- Сравнение EXPLAIN ANALYZE реальных путей поиска на значимых объёмах до/после индексов.
- Запись результатов, повторная проверка перед применением, конкуренция и устаревание данных.
- Бенчмарки 1k/10k/100k, разные потоки и реальные CPU-квоты, прогрев, повторения и метрики.

Ни качество на большой выборке, ни требование 100 000 операций за 20 минут на двух CPU
на этом этапе не измерялись. Эталоны базовых контрольных примеров сохранены в [cases.csv](src/test/resources/cases.csv); актуальное принятие движка отражено в [Final Acceptance](stage6/final-acceptance/FINAL_ACCEPTANCE.md).
