# Схема MySQL и история Flyway

Основное приложение использует схему `alpha_matcher`. Это имя задано исходной V1 и `database/schema.sql`. Прежний URL по умолчанию выбирал `alpha_matcher_dev`, хотя V1 выполняла `USE alpha_matcher`. В результате бизнес-таблицы и `flyway_schema_history` могли оказаться в разных схемах.

V1 сохранена без изменений: её checksum и история применённых миграций не переписываются. Миграции V2-V7 добавляют хранение массового предпросмотра и исполнения, индексы реестров и поиска кандидатов. Для новой установки V1 выполняется первой и по-прежнему требует каталог alpha_matcher.

## Новая установка

Администратор заранее создаёт пустую `alpha_matcher` на выбранном MySQL и выдаёт миграционной учётной записи необходимые DDL/DML-права только на неё. Приложение подключается к существующей схеме; автоматическое создание схем Flyway отключено. `DB_URL` может менять сервер, порт и параметры подключения, но каталог должен оставаться `alpha_matcher`.

До `migrate()` проверяются каталог подключения приложения, каталог отдельного Flyway DataSource (если настроен), `default-schema` и `schemas`. Иное или отсутствующее имя каталога приводит к отказу без вызова миграции. Исторический `CREATE DATABASE IF NOT EXISTS alpha_matcher` остаётся в V1, но при корректном подключении эта схема уже существует; переключения на другую схему не происходит.

Имя пользователя `alpha_matcher_dev` оставлено для совместимости. Оно не определяет имя БД. Профиль `demo` исключает JDBC/Flyway-автоконфигурацию Spring Boot 4 и не требует MySQL.

## Существующие установки

Не менять URL на рабочей установке вслепую. Без подключения к пользовательским БД их фактическое состояние установить нельзя. Ответственный администратор сначала проверяет только чтением:

- где находятся бизнес-таблицы и есть ли данные одновременно в обеих схемах;
- где находится `flyway_schema_history`, успешность V1 и её checksum;
- соответствует ли фактическая структура исходной V1;
- какой сервер и каталог реально использует приложение, есть ли актуальное проверенное резервное восстановление.

Далее выбрать подходящий вариант:

| Состояние | Действие |
| --- | --- |
| Таблицы и успешная V1 находятся в `alpha_matcher` | Использовать URL с `alpha_matcher`; Flyway валидирует прежнюю историю и не повторяет V1. |
| Бизнес-таблицы в `alpha_matcher`, история в `alpha_matcher_dev` | Остановить запись и составить отдельный план согласования истории после сравнения структуры/checksum. Автоматического переноса истории нет. Прямой запуск на непустой схеме без истории должен остановиться; `baseline-on-migrate` не включён. |
| Таблицы/данные в `alpha_matcher_dev`, в обеих схемах или V1 применена частично | Подготовить отдельный план переноса/сверки на копии после инвентаризации данных, внешних ключей и истории. До его принятия приложение с таким URL отклоняет миграции. |
| Структура создана вручную без Flyway history | Сначала доказать её соответствие V1 на копии; вопрос baseline решать отдельно. Не запускать V1 поверх существующих таблиц. |

Это изменение не переносит и не удаляет таблицы/данные, не выполняет `repair`, baseline или изменение checksum. Для схем с другим именем потребуется отдельное решение о версионировании миграций; изменение старой V1 не является безопасным универсальным решением.
